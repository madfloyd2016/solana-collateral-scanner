# v0.4 Asset Identity Dataflow Model

## Purpose

The v0.4 pass attempts to move beyond keyword co-occurrence. It builds a conservative source-level provenance graph for each financial instruction entrypoint and reports how recognizable asset identity and valuation inputs reach selected sinks.

## Tracked provenance labels

- `actual_token_account`: source/user/depositor token-account-like value.
- `actual_mint`: Mint read from a token-account-like source or passed as an explicitly named source Mint.
- `config_object`: market/reserve/bank/config object or loader result.
- `config_mint`: Mint field derived from a config/reserve/market/bank object.
- `config_oracle`: configured oracle identity, such as `bank.primary_oracle`.
- `oracle_account`: oracle/feed account argument or account-like variable.
- `oracle_value`: price/TWAP value read from an oracle path.
- `config_decimals`, `mint_decimals`, `decimal_value`: decimal/precision values.
- `amount_input`: amount/principal/atoms/shares-like input.

## Graph construction

1. Reuse the existing Rust function and Anchor account-context extractor.
2. Parse simple `let` and reassignment statements into local variable dependency edges.
3. Seed provenance from recognizable variable names, account paths, field reads and function parameters/types.
4. Resolve helper calls conservatively: prefer same-file functions; skip ambiguous cross-file names. Map caller argument variables to callee parameters.
5. Add common helper return-expression dependencies for explicit `return value;` and tail expressions such as `Ok(value)`.
6. Iterate provenance propagation to a fixed point over the bounded reachable helper graph.
7. Detect explicit comparison expressions and selected Anchor context equality patterns.
8. Detect valuation/health/borrow/liquidation/withdraw sinks and report the provenance labels reaching their arguments or assigned values.
9. Separately map state-struct fields initialized/written in one function and read in another function. This is a cross-instruction candidate map, not a value-level proof.

## Status semantics

- `potential_unbound_mint_to_config_value_flow_review_required`: actual Mint and config Mint provenance were both identified; config-derived provenance reaches a recognized sink; no matching equality guard was observed in the analyzed scope. Review urgently, but do not call it a confirmed bug.
- `binding_guard_and_config_value_flow_observed_manual_validation_required`: a comparison pattern was found. Verify the exact account keys, error behavior, ordering, and all reachable paths.
- `actual_mint_seen_config_identity_unresolved`: source Mint and config-derived sink flow exist, but config Mint identity was not resolved.
- `config_to_value_flow_observed_actual_mint_source_unresolved`: config-derived data reaches a sink but source token-account Mint provenance was not identified.
- `identity_sources_seen_no_config_value_sink_flow`: both identity roles were observed but no recognized config-to-sink flow was found.
- `insufficient_identity_dataflow_evidence`: the source shape did not expose enough recognizable dataflow to classify the path.

## Limits

This is not compiler-grade Rust MIR/SSA analysis. It does not fully model control-flow dominance, path conditions, borrow semantics, trait dispatch, macros, generated code, CPI behavior, account deserialization, PDA derivations, aliasing, serialization, cross-crate dataflow, or arbitrary return/control-flow behavior. Function-name and variable-name heuristics can over-approximate dependencies. The state-field map links struct and field names but does not prove the same runtime PDA/account instance or value continuity. Pattern presence is not proof of an enforced invariant; missing patterns are not proof of exploitability.

## yDelta regression note

The yDelta fixed-rate review in `audit/ydelta-fixed-rate-review.md` is based on user-supplied manual code-review notes. The v0.4 yDelta-style test is a synthetic pattern fixture only; it is not yDelta source and does not establish source-to-deployment equivalence. Withdraw/Redeem, P2Pool, liquidation/settlement and the protocol-specific local harness remain open work.
